# 寒窗 1.4.4

修的是上一个版本里最影响使用的一件事：**导入一整个文件夹，几乎一半课件提示「处理进程失败」。**

## 根因

整文件夹导入时，34 份课件在 5 秒内全部进入解析，每一份都立刻 fork 一个独立进程。每份 80 页 PDF 会边解析边在内存里攒页面文本、字体、绘图指令和预览位图；几十个进程同时跑，内存峰值直接顶到机器上限，进程被系统杀掉，任务就记成 `PARSE_FAILED / 处理进程失败`。

日志里能看到很典型的一组：55/62、41/42、69/70 这些「跑到一半突然没了」的进度——不是文件坏了，是进程被系统回收。单独把同一份 PDF 交给一个解析进程跑，5–6 秒就能完整读完。

## 改了什么

1. **解析任务排队**：默认同时只跑 1 个解析进程，其余排队；`HANCHUANG_PARSE_CONCURRENCY=2` 可提速（不建议更高）。
2. **每页解析完立即释放**：pdf.js 的页级缓存（图、字体、绘图指令）读完一页就 `cleanup()`，不再攒到 60 页以后才释放。
3. **进程非正常退出自动重试一次**：换一个新进程重跑；第二次仍退出才报错，并在数据库里留下技术原因。
4. **单进程堆上限 512MB → 1GB**。
5. 失败文案改准确：区分「进程中途退出（自动重试过）」与「两次中途退出，暂时读不完」，不再笼统写「处理进程失败」。

## 实测

- 你导入的那批 34 份课件里，原本 16 份 failed、11 份 partial、7 份 ready。
- 用 1.4.4 逐份重试后：**0 份 failed，24 份 partial，9 份 ready**。partial 不是失败，是这些页里含图片、在没配读图模型时标记为「待复核」，文字层已可用。
- 新增回归测试：三份同时导入时只启动一个解析进程，前一份结束后才放行下一份。
- `npx vitest run`：58 个测试文件、346 项通过。
